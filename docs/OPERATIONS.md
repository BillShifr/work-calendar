# Эксплуатация

## Развёртывание

1. Создать отдельного пользователя и каталог продукта; заполнить `.env` длинным паролем PostgreSQL.
2. Перед миграцией выполнить `scripts/backup.sh` и проверить архив через `pg_restore --list`.
3. Запустить БД, применить `npm run db:migrate`, затем поднять приложение.
4. Установить `deploy/nginx/time.tfoms.conf`, добавить внутреннюю DNS-запись `time.tfoms`, проверить `/api/health`.
5. Создать кадрового администратора через seed только при первом развёртывании, затем немедленно сменить пароль.

Приложение запускается без root, с read-only filesystem, удалёнными Linux capabilities и отдельной сетью. Production cookie должна иметь `Secure=true` после включения TLS.

## Backup и восстановление

Ежедневный custom-format backup хранится вне хоста приложения с ротацией согласно политике организации. Раз в квартал выполняется тестовое восстановление в изолированную БД и проверка числа пользователей, ревизий и audit events. Restore никогда не выполняется поверх production без окна работ и подтверждённого backup.

## Наблюдаемость

Контролируются доступность `/api/health`, p95 latency чтения/записи, доля 5xx, ошибки конфликтов версий, длина outbox и возраст необработанного события. Логи не содержат пароли, cookie, токены и содержимое кадровых записей.

## Откат

Версия приложения откатывается только если применённая миграция обратно совместима. При несовместимой миграции используется исправляющий forward-релиз; восстановление старого образа после частично применённой схемы запрещено.
