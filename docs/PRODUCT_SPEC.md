# TFOMS Time — продуктовая спецификация

## Назначение

Самостоятельный внутренний продукт для ежемесячного учёта внеурочного времени и ежегодного планирования отпусков. Он не является модулем другой системы.

## Роли

| Возможность         | Сотрудник              | Руководитель подразделения           | Кадровик                                  | Руководитель кадров           | Администратор                 |
| ------------------- | ---------------------- | ------------------------------------ | ----------------------------------------- | ----------------------------- | ----------------------------- |
| Свои отчёты и планы | CRUD до согласования   | собственные записи                   | просмотр и предложение правки             | просмотр и предложение правки | нет скрытой предметной правки |
| Утверждение         | подтверждает правку HR | согласует кварт своего подразделения | работает только с согласованным кварталом | то же по всей организации     | нет                           |
| Справочники         | нет                    | нет                                  | подразделения, штат и должности           | плюс HR-роли                  | учётные записи и настройки    |
| Аналитика и экспорт | только свои данные     | состояние кварталов своего отдела    | свод и Excel по организации               | вся организация               | технический аудит             |

Права проверяются на сервере для каждого маршрута. Удаление сотрудников запрещено: применяется блокировка с сохранением истории.

## Состояния согласования

`draft → submitted → approved`

`submitted → hr_proposed → approved | submitted`

`submitted → rejected`, `submitted → withdrawn`, `approved → reopened`.

Каждая предметная правка создаёт новую неизменяемую ревизию. HR обязан указать причину. Конкурирующие записи защищены номером версии и транзакционной блокировкой.

## Ключевые сценарии

1. Сотрудник открывает месяц, выбирает день и одно из значений 5/10/15/30/60 минут, затем отправляет отчёт или явно подтверждает ноль.
2. Назначенный согласующий (по умолчанию руководитель подразделения) видит комплектность трёх месяцев квартала, проверяет отчёты и нажимает «Согласовано».
3. Только после квартального согласования отчёты попадают в очередь HR; кадровик может утвердить или предложить исправление, а сотрудник — подтвердить либо создать встречную версию.
4. Сотрудник в годовой матрице выбирает начало и конец одного или нескольких отпусков; первая ячейка подсвечивается сразу.
5. HR видит пересечения по отделам, кадровый остаток и правила критичности.
6. HR задаёт норматив дней по должности и индивидуальные значения по сотруднику, видит кварталы и выгружает XLSX структуры утверждённого шаблона.

## Нефункциональные требования

- WCAG 2.2 AA, управление клавиатурой, touch target от 44×44 px, масштаб 200%.
- p95 чтения до 300 мс, записи до 500 мс; один запрос на календарь, серверная пагинация очередей.
- 5 000 сотрудников, 100 отделов, 10 лет истории.
- Часовой пояс предметных дат: `Asia/Yekaterinburg`.
- Логи без паролей, cookie и персональных данных; аудит, outbox и резервное копирование обязательны.

## Production-критерий продукта

- Продукт не содержит мок-данных, демонстрационных показателей и фиктивных пользовательских сценариев.
- Любое действие в UI существует только при наличии реальной end-to-end реализации: серверные права, валидация, постоянное хранение, аудит, обработка ошибок и проверка сценария.
- Нереализованные возможности не показываются пользователю в виде заглушек, отключённых кнопок, обещаний «скоро» или элементов без обработчика.
- Интерфейс не содержит презентационного текста, технических номеров и необязательных подсказок. Допустимы только короткие контекстные сообщения, предотвращающие конкретную ошибку или объясняющие необходимый следующий шаг.
- Все незавершённые возможности и решения фиксируются только в roadmap и разделе `Висяки и открытые решения` до их полной реализации.

## Выполнено

- 2026-10-30 — Docker runtime build перестал зависеть от локального пустого каталога `public`: builder сам создаёт опциональный каталог Next.js, поэтому чистый GitHub checkout и локальная сборка используют один контракт.
- 2026-10-30 — из кадрового XLSX подготовлен идемпотентный production seed: 31 подразделение с иерархией филиалов и 21 нормализованная должность с базовыми нормативами; ФИО и тестовые отчёты в production seed не входят.
- 2026-10-30 — уникальность подразделения переведена с плоского названия на сочетание «организация + родитель + название», поэтому одинаковые «Руководство» и профильные отделы разных филиалов хранятся без искажения структуры.
- 2026-10-30 — подготовлен production release-контур по модели Kanban: GitHub Actions проверяет и публикует два immutable-образа по SHA и deployment bundle, а production обновляется оператором вручную с обязательными checksum, backup до миграций, reference seed и readiness.

## Правило ведения документа

Любая следующая реализация должна одновременно обновлять статус roadmap, список выполненного и висяки. Нельзя помечать этап готовым только по наличию интерфейса: должны быть серверные права, сохранение данных и соответствующая проверка.
